# EVE Healthcare — Diagnostic Bookings & Payments Backend

FastAPI backend for diagnostic test bookings with a simulated payment service and an idempotent payment webhook. Built for the EVE Healthcare SDE Intern backend assignment.

## Quick start (Docker — recommended)

```bash
docker compose up --build
```

- API: http://localhost:8000
- Swagger/OpenAPI docs: http://localhost:8000/docs
- Postgres 16 (alpine) with a named volume, API seeds admin + sample centres/tests on boot.

Default seeded admin: `admin@eve.local` / `admin12345` (change via env).

## Quick start (local, without Docker)

Requires Python 3.12+ and a PostgreSQL instance, or set a SQLite URL to try it instantly.

```bash
python -m venv .venv
.venv\Scripts\pip install -r requirements.txt      # Linux/mac: .venv/bin/pip
copy .env.example .env                              # edit DATABASE_URL / secrets
.venv\Scripts\python -m app.seed                    # optional: seed admin + sample data
.venv\Scripts\uvicorn app.main:app --reload
```

SQLite fallback (no Postgres needed): set `DATABASE_URL=sqlite:///./eve.db`.

## API endpoints

| Method & path | Auth | Purpose |
| --- | --- | --- |
| `POST /auth/signup` | public (rate-limited) | create user |
| `POST /auth/login` | public (rate-limited) | returns JWT |
| `GET /centres`, `GET /centres/{id}`, `GET /tests` | public | browse centres, tests, prices |

| `POST /admin/tests` | admin | create diagnostic test |

| `POST /bookings/{id}/cancel` | owner/admin | cancel PENDING/CONFIRMED booking |
| `POST /payments` | owner/admin (rate-limited) | simulate payment |
| `GET /payments/{id}` | owner/admin | payment detail |
| `POST /payments/webhook` | HMAC signature | provider payment-status callback (idempotent) |

### Example flow

```bash
# 1. Sign up + login
curl -X POST localhost:8000/auth/signup -H "Content-Type: application/json" \
  -d '{"full_name":"Asha","email":"asha@example.com","password":"password123"}'
curl -X POST localhost:8000/auth/login -H "Content-Type: application/json" \
  -d '{"email":"asha@example.com","password":"password123"}'
TOKEN=...

# 2. Book CBC at centre 1 (price is taken from the DB, never the client)
curl -X POST localhost:8000/bookings -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"centre_id":1,"test_id":1,"appointment":"2026-10-10T10:00:00+05:30"}'

# 3. Pay (deterministic for demos/tests: force_status, default random)
curl -X POST localhost:8000/payments -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"booking_id":1,"force_status":"SUCCESS"}'

# 4. Or let the simulated provider call the webhook (payment stays PENDING ~1.5s)
curl -X POST localhost:8000/payments -H "Authorization: Bearer $TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"booking_id":1,"mode":"webhook","force_status":"SUCCESS"}'

# Webhook (provider side) — HMAC-SHA256 hex of the raw body in X-Webhook-Signature
SIG=$(python -c "import hmac,hashlib;print(hmac.new(b'whsec-change-me',b'{\"event_id\":\"evt_1\",\"payment_id\":1,\"status\":\"SUCCESS\"}',hashlib.sha256).hexdigest())")
curl -X POST localhost:8000/payments/webhook -H "X-Webhook-Signature: $SIG" \
  -H "Content-Type: application/json" \
  -d '{"event_id":"evt_1","payment_id":1,"status":"SUCCESS"}'
```

Re-send the same webhook body — the response is `{"processed": false, "reason": "ALREADY_PROCESSED"}` and nothing changes.

## Database design

```
users(id, email unique, full_name, password_hash, is_admin, created_at)
tests(id, name unique, description)
centres(id, name, location, created_at)
centre_tests(id, centre_id FK, test_id FK, price_paise, UNIQUE(centre_id, test_id))
bookings(id, user_id FK, centre_test_id FK, appointment, amount_paise, status, created_at, updated_at)
payments(id, booking_id FK, amount_paise, status, provider_reference unique, created_at, updated_at)
webhook_events(event_id PK, payment_id FK nullable, payload JSON, status, attempts, next_retry_at, last_error, ...)
```

- Price belongs to the centre-test pair — the same test can cost differently per centre.
- Money stored as integer paise; API shows rupees (`500.00`).
- Booking amount is a snapshot of the centre-test price at booking time.
- Booking states: `PENDING → CONFIRMED | FAILED | CANCELLED`, plus `CONFIRMED → CANCELLED`. Any other transition → 409.

## Key design decisions & assumptions

1. **Payment flow** — `POST /payments` (mode `direct`, default) simulates processing synchronously and atomically updates payment + booking in one transaction. Mode `webhook` leaves the payment `PENDING` and the simulated provider delivers an event to `POST /payments/webhook` ~1.5s later, exercising the real webhook path.
2. **Idempotency** — `webhook_events.event_id` is the primary key. First delivery inserts the event, then processes it in one transaction. Duplicates get `200 {"processed": false}` with no state change. Conflicting status for an already-final payment is stored as `PERMANENTLY_FAILED` — never applied.
3. **Webhook retries** — events that reference a not-yet-known payment (or hit a transient error) are stored and retried by an in-process background loop with exponential backoff (2^n seconds, max 5 attempts), then marked `PERMANENTLY_FAILED`. `# ponytail:` in-process only — swap to Celery/Redis if multiple workers are needed.
4. **Webhook security** — `X-Webhook-Signature` must be the HMAC-SHA256 hex digest of the raw request body using `WEBHOOK_SECRET`; verified with `hmac.compare_digest`.
5. **Slots** — one active booking (`PENDING`/`CONFIRMED`) per centre per exact appointment time. Cancelled bookings free the slot. Past appointments are rejected. Centre row is locked with `SELECT ... FOR UPDATE` on Postgres during booking to avoid races.
6. **Payments** — one attempt per booking; a failed payment leaves the booking `FAILED` (book again rather than retry). Cancelling is blocked while a payment is `PENDING` for that booking.
7. **Rate limiting** — in-memory sliding window per IP on auth/payment endpoints (`# ponytail:` single-process; use Redis for multi-worker).
8. **Admin** — seeded `is_admin` user manages centres/tests/prices. Regular users can only read.
9. Schema is created with `create_all` on startup; no Alembic (noted as an improvement).

## Tests

```bash
.venv\Scripts\python -m pytest tests -q      # Linux/mac: .venv/bin/python -m pytest tests -q
```

52 tests, SQLite in-memory-style temp file (no Docker needed): auth (signup/login/dup/bad creds/401s/rate limit), bookings (validity, availability, slot conflicts, ownership, cancellation, admin authz), payments (success/failed/repeat/ownership), webhooks (idempotency, conflict, unknown payment, signature, amount mismatch, retry/backoff/max-attempts).

## What I would improve with more time

- Alembic migrations instead of `create_all`
- Redis-backed rate limiting + cache for centre listings, pagination on list endpoints
- Celery for webhook retries to support multiple workers
- Structured JSON logging, refresh tokens, CI workflow
- Webhook payload schema versioning and replay/admin endpoint for dead-letter events
